# Тест-план і стан перевірок

[Навігація](README.md) · [Вимоги](technical-specification.md)

## Автоматичні перевірки

З кореня репозиторію після `pnpm install --frozen-lockfile`:

```powershell
pnpm test
pnpm build
pnpm format:check
```

Повторний запуск **28.09.2026** у межах підготовки документації:

| Перевірка                             | Результат      |
| ------------------------------------- | -------------- |
| API: Node test runner через tsx       | 13/13 пройдено |
| Web: Vitest, включно з React/jsdom    | 28/28 пройдено |
| Production build API + web            | Успішно        |
| Prettier для коду за кореневим script | Успішно        |

41 тест не є гарантією відсутності помилок. Тести не перевіряють повністю зовнішні live-сервіси, публічне розгортання, відновлення backup чи всі браузери. Кореневий `format:check` не включає Markdown.

## Ручні інтеграційні сценарії

Виконуйте операції запису в окремій тестовій БД. Не використовуйте персональні дані; заміну й видалення перевіряйте лише на наборах, створених для тесту. Нижче — план, а не твердження, що всі сценарії повторно виконані сьогодні.

| ID   | Дія                                                      | Очікуваний результат                                                                 |
| ---- | -------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| M-01 | Новий порожній Docker-том, setup, повний запуск          | Три healthy-сервіси, seed у «Тестові», вхід admin із локальних секретів              |
| M-02 | Перемикання джерел, у т.ч. швидке                        | Дані відповідають останній категорії, старі відповіді не підміняють її               |
| M-03 | Фільтри й експорт                                        | Нижні метрики/графіки та CSV збігаються з відбором; верхнє коло має відоме обмеження |
| M-04 | ЄДЕБО/Eurostat                                           | Відповідні типи показників; немає вигаданого гендеру/ЗВО                             |
| M-05 | Реєстрація, вхід, неправильний пароль, гість у admin API | Ролі й HTTP-коди відповідають контракту                                              |
| M-06 | Профіль без згоди, зі згодою, повторне подання           | Валідація; один запис; публікація лише груп від 5                                    |
| M-07 | Створення/приховування категорії                         | Прихована категорія відсутня у списку та повертає 404 на dashboard                   |
| M-08 | Джерело з новою категорією, вимкнення, видалення з FK    | Атомарність створення; 503 без live-джерела; 409 для залежного запису                |
| M-09 | Коректний CSV на 15 000 унікальних рядків                | Preview показує кількість; імпорт повертає 15 000; суми збігаються                   |
| M-10 | Подвійний submit, успіх, помилка, повторний вибір файлу  | Один запит у busy-стані; очищення тільки після успіху                                |
| M-11 | 20 001 рядок, невалідний рік/число, дублікати, >10 МіБ   | Відмова до запису або відповідний 400/409/413; немає часткового набору               |
| M-12 | Успішна й невдала заміна тестового набору                | COMMIT замінює; ROLLBACK зберігає старі записи                                       |
| M-13 | UI на 375/800/1024/1440 px, довгі назви й URL            | Немає горизонтального overflow сторінки; кнопки в межах картки                       |
| M-14 | Теми, обидві мови, клавіатура                            | Читабельний UI, доступні основні дії й стан імпорту                                  |
| M-15 | Зупинка/старт Compose, backup і restore в окрему БД      | Дані зберігаються; копія відновлюється та дає контрольні суми                        |

Для кожного запуску фіксуйте дату, commit, середовище, дії, очікуваний/фактичний результат, HTTP-код і screenshot за потреби. Не записуйте пароль/JWT у звіт.

## Історія локального аудиту

За локальними журналами від **09.09.2026** попередній запуск мав 27/27 API та 10/10 browser перевірок. Це історичний результат, **не актуальний повний повторний аудит** після всіх UI-змін.

У старому browser-аудиті B05 і B09 очікують початково заповнений CSV. Тепер форма порожня: B05 має явно завантажити валідний CSV, B09 — явно ввести CSV з невалідним роком. Без цього B05 не виконає імпорт, а B09 може пройти без перевірки року. Ці сценарії потрібно адаптувати перед повторним прогоном; у цій документаційній задачі їх не змінено.

`audit/` і `docker-compose.adversarial.yml` навмисно не відстежуються Git. У чистому клоні їх немає, тому вони не є обов'язковою залежністю запуску/CI. Якщо локальний комплект є, порядок повторного аудиту наведено в [безпеці](security.md).

## CI та критерій готовності

[GitHub Actions](../.github/workflows/verify.yml) працює на push/PR до `main`: Node.js 22, pnpm 11.19.0, frozen-lockfile, тести, build. Форматування, Docker end-to-end, браузерні сценарії та dependency security audit окремими кроками workflow не задані.

Для локального випуску потрібні зелені автоматичні перевірки, виконані критичні M-01/M-05/M-07/M-09–M-12, підтверджений backup/restore та перелік відкритих обмежень. Перед публічним доступом потрібен окремий актуальний security review. Наявність цього документа не означає проходження всіх критеріїв.
